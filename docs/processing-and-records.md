# 質問から回答までの処理と記録

## 処理の流れ

1. アプリが認証・設定・利用上限を確認し、必要に応じて保存会話を復元する。質問送信時にターンIDを発行し、質問ログと処理開始時の会話を保存する。
2. 会話・未解決事項・保存結果を同期する。Interactions APIの状態IDが有効なら新しい質問・ツール結果だけを追加する。期限切れや入力予算到達時などは、要点と保存結果IDから状態を作り直す。API側が保持する文脈も入力トークンの計数対象になるため、差分送信量と入力トークン数は一致しない。
3. 共通指示と必要なツール定義を準備し、AIを呼ぶ。必要な定義が未選択なら、AIがselect_toolsを呼び、その後のAI呼び出しに定義を渡す。この選択も1回のAI呼び出しを使う。
4. AI応答の使用量を集計する。429の場合だけ制限付きで待機・再試行する。タイムアウトや他のエラーを無条件に再試行することはない。モデルの終了理由や応答形式を検査する。
5. ツール要求があれば実行する。保存結果の参照・ローカル分析は新たなBigQueryクエリを実行しない。スキーマ・一覧・同一SQL結果はキャッシュを再利用する。実行済みの同じツール要求も保存した応答を再利用する。
6. 新しいSQLは読み取り専用・許可対象などを検査し、テーブル名が確認済みか調べる。未確認なら一覧を取得し、存在しない名前を拒否する。BigQueryのdry runで構文・列・推定スキャン量を確認する。確認が必要な費用の場合はユーザーの判断を待つ。承認後に実行して結果を保存する。
7. 結果を行数・型・統計・上限付きCSVなどにしてAIに返す。SQLと取得済みDataFrameはアプリ側に残す。要点メモと結果IDを更新し、必要なら次のAI呼び出しに進む。ツールエラーもAIへ返し、修正を試みる。
8. 最終回答または確認質問を表示する。図表・データ・実行詳細を描画し、会話・結果・実行イベントを保存する。停止・例外も表示と保存の対象になる。

## 何が記録されるか

| 対象 | 保存先・内容 | 時間の記録 |
| --- | --- | --- |
| 質問 | 質問ログ、保存会話 | 送信日時。今回からターン開始時刻も保存 |
| AIの要求・応答 | 保存会話のモデル応答・ツール要求、API状態ID。各HTTP要求の完全な送信本文を逐一保存するものではない | 今回から各AI呼び出しの開始日時・経過秒。通信、準備、再試行を含む |
| AI使用量 | BigQuery利用ログと会話の累計。今回から各呼び出しの使用量も会話に保存 | 利用ログのイベント日時。これは所要時間ではない |
| ツール実行 | 保存会話、アプリログ。一覧・スキーマ・SQL結果のキャッシュ、エラー。今回から回答ごとの実行イベントも保存 | 各ツールの経過秒。今回から開始日時・停止・実行確認待ちへの移行も保存 |
| SQL実行 | SQL、結果、推定量・課金対象バイト数など。成功した新規クエリは利用ログにも記録 | 成功した実行のexecution_seconds。dry runと取得等を含むツール全体の時間は別 |
| 保存結果のローカル分析 | 手法・条件・結果・エラー | 分析秒数とツール全体の秒数 |
| 429の再試行 | アプリログ。今回から実際の待機秒・再試行番号も会話に保存 | 待機秒。AI呼び出し時間の内数であり加算すると二重計上になる |
| 回答 | 本文、図表用データ、今回からターンID・実行イベント | 今回から質問送信～回答処理終了の経過秒。確認待ちを含む。最後の保存・画面描画の完了までは含まない |
| モデル内部の思考 | 内部状態・思考の全文は取得・記録しない。API状態IDは内部状態の中身ではない | 思考時間は取得できない。思考トークン数もAPIから返らなければ不明 |

すべての処理を完全に記録しているわけではない。認証、履歴復元、圧縮、課金ログ書き込み、会話の保存、画面描画などを個別の時間として測定していない。AI呼び出し時間からモデルの計算時間と通信・サーバー待ち時間を分離することもできない。トークン数はAI APIの応答から取得し、BigQueryやローカル分析のCPU処理にはトークンは発生しない。結果を次のAI呼び出しに含めたときに入力トークンとして計数される。

今回追加した時間・イベントの保存先は会話履歴であり、BigQuery利用ログに所要時間の列は追加していない。利用ログは失敗してもチャットを止めない設計で、連続失敗時は記録を停止する。会話保存に失敗した場合や、処理途中でプロセスが終了した場合には記録が欠ける可能性がある。過去の未計測時間は後から復元できない。

「データ・実行詳細」は以前、成功したSQL結果もローカル分析結果もない場合に非表示になっていた。今回から結果がない失敗ターンや通常回答でも、ターンID・実行イベント等があれば表示する。ターンIDは折りたたみ内の小さな説明に表示する。古い回答に保存されていないID・時間を推測して補完しない。

## データセットとテーブル確認

既定のデータセットは202506。明示的な環境設定・別の指定は設定上の許可範囲で扱う。既知のデータセットを探すためにlist_datasetsを繰り返す必要はない。

テーブル名を推測しない。既存の一覧キャッシュまたは取得済みスキーマで実在が分かっていれば再取得しない。未確認なら一覧を取得して照合する。スキーマ取得と新規SQL実行の両方で照合し、一覧にないテーブルは実行前に拒否する。これらのキャッシュは会話履歴とともに保存・復元される。列名・値は別途スキーマや必要最小限のクエリで確認する。

## スキーマの先読み・回答の根拠確認

- 分析対象が明確な質問では、確認済みのテーブル名との一致と限定した業務用語の対応から、関連スキーマを最大3テーブル先読みする。テーブル一覧に存在しない名前を推測して取得しない。既存の一覧・スキーマを再利用し、関係が曖昧なテーブルの全件取得はしない。
- 先読み済みテーブル名をAIに知らせ、run_queryを選んだ呼び出しでは必要な列名・型を短く添える。生成されたSQLで別の表を使う場合も、実行前にその表のスキーマを取得する。
- 単純な表・CTE・別名・結合の列参照は構文木とスキーマで照合する。不明な列があれば確認済み列名とともにエラーを返す。構造体・UNNESTなど複雑なSQLは、従来どおりBigQueryのdry runで最終検証する。
- 同じターンで失敗したSQLは、空白やコメントだけ変えても再実行しない。SQLを修正するか、次のターンで再調査する。
- 分析回答のfinish_answerでは、要点メモの参照IDが実在し、アプリが保持する成功したSQL結果・保存済み表・分析結果につながることを検証する。テーブル一覧・スキーマ・失敗した結果だけを数値の根拠にはできない。失敗結果を確定事項のメモに引用することも拒否する。
- データ分析中にfinish_answerを使わず通常の文章で回答した場合は、根拠未検証の回答を表示せず、定型の案内に置き換える。元のAPI応答は状態IDの連続性を保つために内部履歴に残し、次回には表示を見送った案内だけを追加する。途中で出力上限に達した分析回答も未検証の文章を表示しない。
- アプリが確認した処理の成否・結果ID・次の行動を、APIへ渡す実行状態として保存する。モデルが作る要約とは分け、失敗した取得を成功したように引き継がない。
- 「データ・実行詳細」内の「引き継ぎ要約」に、実行状態の要約、今回の要約、会話全体の要約、AIの作業メモと参照ID、処理の成否・エラー、次の行動を表示する。モデルから要約を取得できなかった場合は、その欄を捏造せず実行状態を表示する。表示内容は回答ごとのスナップショットとして保存し、次ターンの更新で過去の表示を書き換えない。

根拠IDの検証は、回答の参照先が実在する成功結果であることを確認する。各文章の意味やすべての数値が参照先と一致することを、意味解析で完全に証明する機能ではない。
