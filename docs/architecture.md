# 仕組み

[README](../README.md) の続き。ShiruGPT の内部構造の詳細解説です。

## チャットコマンド

`/help`・`/new`・`/usage` は入力を会話本文に追加する前にアプリ内で処理し、
Geminiや質問ログへ送信しません。不明なスラッシュコマンドもモデルへ送りません。
月次上限到達時や確認待ちでもコマンドを利用できます。`/new` は未保存の履歴が
保存できなければ会話を維持します。

チャット入力で `/` を打つと入力欄の上に候補を表示し、入力した接頭辞で絞り込みます。
クリック、または上下キーとEnterでその場で実行します。数字キーでの選択は行いません。Tabは入力補完のみ、Escで閉じます。
候補表示はStreamlit v2コンポーネントを使いブラウザ内で処理するため、入力ごとのPython再実行や
Gemini呼び出しはありません。標準のチャット入力とHigh時の枠色は維持します。

`/usage` は当月の利用額・上限・残額・日本時間の次回リセット日時と、会話全体の
入力・出力トークン、BigQuery課金対象量、Gemini・BigQuery別の推定費用を表示します。
思考トークンは出力に含め、内訳は表示しません。モデル・リージョン別の入力・出力単価と
BigQuery単価も表示し、金額は数式への誤変換を避けるためUSD表記にします。
ログイン本人の当月分（日本時間）と全期間のログを集計し、会話数・質問数、トークン数、
AI呼び出し・クエリ回数、課金対象量、Gemini・BigQuery別の費用と合計を表示します。
会話数は質問ログのsession_id、質問数はturn_idの重複を除いた数です。確認への回答も1件に数え、
コマンドは含めません。会話を削除してもログが残っていれば累計に含めます。
全期間は記録されているログ全体であり、記録開始前・欠落分は含みません。
質問と費用を別々に集計してから結合し、イベント数の違いによる二重計上を防ぎます。利用がなければ0です。
詳細は取得時点のログに基づき、利用ログ未設定時は表示しません。
集計はアプリ側の固定SQLで行い、Geminiへは送りません。
`/model` は使用中のモデルを表示します。既定モデルはGemini 3.8 Flashです。
`/usage`や`/model`などの説明表示は「閉じる」、空の入力欄でのEnter、質問の送信で閉じます。
入力済みの質問の送信や自由記述欄の改行、コマンド候補の確定を妨げません。

`/effort` はコマンド候補と同じポップアップで「1. Low／2. Medium／3. High」を表示します。
数字キー1〜3で即確定でき、↑↓・Enter・クリックでも選べます。IME変換中や修飾キー付きの入力は奪いません。
Escで閉じます。変更後の通知は表示せず、その場で適用します。
引数は受け付けません。会話・取得結果は維持し、APIのthinking_levelのみを変更します。
入力欄の枠はLow＝緑、Medium＝青、High＝紫で、角まで色を付けて常時表示します。
フォーカス時も同じ色を維持し、標準の赤い枠に重ねて別の枠を描かないようにしています。
ライト・ダーク両テーマに対応し、会話ごとに保存します。新しい会話はLowです。
質問による自動判定や判定用AIへの問い合わせはありません。
旧履歴のauto設定はLowへ移行します。実行確認からの再開はターン開始時の設定を維持します。

`/thinking` は詳細分析モードを切り替えます。有効時は元のeffortを保存してHighにし、
共通指示へ多角的な仮説検証・結論と根拠・限界の説明を求める指示を追加します。
再入力で追加指示を解除し、元のeffortへ戻します。有効中にeffortを手動で変えても追加指示は維持します。
SQLの安全規則、日時の扱い、BigQuery・月次・調査回数の上限はどちらの操作でも変更しません。

確認質問は、数字キーか上下キーとEnterで回答できます。単回答は即送信し、複数回答は
数字で選択・解除してEnterで送信します。クリックでは選択・解除後に送信ボタンを押すため、
自由記述の補足も可能です。文字入力中は通常の入力を優先します。

一般知識を使った課題発見・施策検討・壁打ちもシステム指示に含めています。
実データで確認した事実と一般知識に基づく仮説・提案、未確認の点を区別します。
一般的な相談だけで答えられる場合はBigQueryを使わず、データによる検証が必要になればツールで調べます。
確認質問も、実データの分析条件は先にスキーマを確認し、一般相談の目的・観点はデータ照会なしで確認できます。
外部検索機能は持たず、外部調査や最新情報を確認したようには説明しません。

費用はモデル別に見積もり、3.8 Flashは期間限定還元・キャッシュ割引前の標準単価を使います。
旧2.5の利用ログは従来の単価で集計し、旧履歴には質問・回答・取得結果を引き継ぎます。
モデルが変わった履歴のAPI用文脈は質問と回答から再構築し、旧モデルの署名や未実行の要求を送りません。

停止ボタンは処理中の入力欄の右端で送信矢印と置き換えます。色は画面の文字色に追従し、ライト・ダーク両テーマに対応します。

履歴は最近5件から表示し、控えめな「さらに表示」で5件ずつ同じ一覧に追加します。
最近5件の履歴ZIPはバックグラウンドで先読みし、開いた履歴とともに利用者のセッション内で保持します。
復元時はZIPを読み直して別の会話オブジェクトを作るため、画面での変更がキャッシュへ混ざりません。
保存時は新しい世代のZIPへ更新し、削除時・利用者変更時は対応するキャッシュを消します。
他のタブや端末による変更はキャッシュに即時反映されませんが、保存時の世代番号による競合検出は維持します。

## 1. 全体像

4 つのレイヤーが一方向に連なっています。

```
┌─────────────────────────────────────────────────────┐
│ app.py            Streamlit UI                       │
│                   チャット入力・確認ダイアログ・結果表示    │
└───────────────┬─────────────────────────────────────┘
                │ agent.run(contents, ctx)
┌───────────────▼─────────────────────────────────────┐
│ src/agent.py      Gemini Function Calling ループ      │
│                   ツール呼び出しの往復・中断と再開         │
└───────────────┬─────────────────────────────────────┘
                │ 4 つのツール関数
┌───────────────▼─────────────────────────────────────┐
│ src/bq_tools.py   BigQuery アクセス                   │
│  ├ src/sql_guard.py   実行前の SQL 検査（必ず通る）      │
│  └ src/summarize.py   結果を要約に圧縮                  │
└───────────────┬─────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────┐
│ BigQuery                                             │
└─────────────────────────────────────────────────────┘
```

Gemini は BigQuery に直接触れません。**Gemini がするのは「この関数をこの引数で
呼びたい」という意思表示だけ**で、実際に接続してクエリを走らせるのは
`bq_tools.py` の Python コードです。この分離があるおかげで、SQL の検査・
結果の圧縮・キャッシュ・課金上限といった制御を、すべてこちら側で強制できます。

## 2. 1 回の質問で何が起きるか

「来店データで学年別の来店件数を多い順に教えて」と入力したときのデータ確認の流れです。
表では`select_tools`による初回のツール定義選択・切り替えを省略しています。

| # | 誰が | 何を |
|---|---|---|
| 1 | app.py | 入力を `Content(role="user")` にして `contents` に追記 |
| 2 | Gemini | 「まず何があるか調べたい」→ `list_datasets` を要求 |
| 3 | bq_tools | allowlist 内のデータセットを返す → `202506`（location: US） |
| 4 | Gemini | `list_tables(dataset="202506")` を要求 |
| 5 | bq_tools | 14 テーブルの名前だけを返す（スキーマは含めない） |
| 6 | Gemini | 「`来店` が使えそうだ」→ `get_table_schema(202506, 来店)` を要求 |
| 7 | bq_tools | 14 列の名前と型、行数 838,286、サイズ 149.80 MB を返す |
| 8 | Gemini | 実在する列名 `grade` を使って SQL を生成 → `run_query` を要求 |
| 9 | sql_guard | SELECT 限定・allowlist・複文を検査。`LIMIT 1000` を自動付与 |
| 10 | bq_tools | dry run で 9.58 MB と見積もり → 閾値内なので実行 |
| 11 | summarize | 結果 13 行を「行数・列と型・統計・先頭 15 行」に圧縮 |
| 12 | Gemini | 結果を読んで`finish_answer`で日本語の回答と引き継ぎメモを返す（生成は追加せず終了） |
| 13 | app.py | 回答・実行 SQL・グラフ・表を画面に描画 |

この例のBigQuery用ツールは4回（ステップ3, 5, 7, 10）、最終回答の生成は1回です。
最初に`list_datasets`・`list_tables`・`get_table_schema`を選び、次に`run_query`・
`finish_answer`へ切り替える場合、定義選択の生成が2回加わり、合計7回になります。
既に必要な定義が選択されている場合や、複数の取得をまとめる場合は回数が変わります。
選択ツールはデータを取得せず、アプリ内の定義を次のリクエストへ渡すだけです。
`src/prompts.py`で共通指示とツール別指示も分離し、選択中のツールに必要な指示だけを追加します。
共通指示は全生成に含めますが、読み取り専用・事実確認・日時・未確認事項などに短縮し、
長い施策検討・壁打ちの説明は最終回答時だけ追加します。分析の選択時にSQL構文や回答スタイルは送りません。
複数ツールが必要とする共有指示は一度だけ載せます。詳細分析モードの追加指示は有効時のみです。
SQL・グラフの詳細は`run_query`、確認フォームの詳細は`ask_clarification`、回答・累積要約の詳細は
`finish_answer`の選択時に渡します。複数ツールで共有する指標・日時・メモの指示は一度だけ追加します。

## 3. なぜループするのか

Gemini は「答えるために何が必要か」を 1 回では判断しきれません。上のトレースで
言えば、ステップ 2 の時点ではテーブル名も列名も知らない状態です。ここで SQL を
書かせれば、存在しない列名を推測で使うことになります。

そこで「調べる → 分かったことを踏まえて次を決める」を繰り返させます。
ループは通常、**`finish_answer`が有効な回答とメモを返した時**に終了します。
ツールを使わない通常のテキスト回答も受け付けますが、その場合は要約への置換を行いません。

```python
# src/agent.py: run()
for _ in range(self.settings.max_tool_iterations):   # 暴走防止の上限（既定 50）
    response = self._generate(context_memory.build_request(contents, ctx))
    calls = [p.function_call for p in parts if p.function_call]

    if not calls:
        return self._answer(contents, text, candidate.content)  # 最終回答も履歴に保存

    contents.append(candidate.content)     # Gemini の「呼びたい」を履歴に追記
    responses = [self._dispatch(call, ctx) for call in calls]
    contents.append(Content(role="user", parts=responses))   # 結果を履歴に追記
    # finish_answerが成功した場合は回答を表示して終了（追加の生成なし）
    # それ以外は送信用の履歴を組み立て直し、ループ先頭へ戻る
```

`max_tool_iterations` は、スキーマ取得と SQL 修正を延々と往復するような
状態を打ち切るための保険です。

## 4. 設計の中心 — Gemini 境界を越えるものを絞る

このプロジェクトの設計判断は、ほぼこの一点に集約されます。

| データ | Gemini に渡す | UI に出す |
|---|---|---|
| データセット / テーブル一覧 | ○ | — |
| スキーマ | **明示的に要求された 1 テーブル分のみ** | — |
| クエリ結果 | **要約のみ**（行数・列と型・統計・先頭 N 行） | DataFrame 全体 |

### スキーマの段階的取得

`list_tables` はテーブル**名**だけを返し、列情報は含めません。
列情報が要るテーブルについてだけ、Gemini が改めて `get_table_schema` を呼びます。

全 14 テーブルのスキーマを一括で `SYSTEM_INSTRUCTION` に埋め込めばツールの往復は
減りますが、**関係ないテーブルの列情報まで毎回の呼び出しに乗り続ける**ため、
トータルのトークンはむしろ増えます。加えて BigQuery 側でカラムが変わっても
追従しません。列の意味づけを補いたい場合は、BigQuery のカラム `description` に
設定してください。`get_table_schema` は `description` をそのまま拾って返します。

### クエリ結果の要約

`run_query` の実行結果は、`QueryRun` の中で 2 つに分岐します。

```python
# src/bq_tools.py: execute()
df = rows.to_dataframe(create_bqstorage_client=False)   # 生の DataFrame
summary = summarize_dataframe(df, sample_rows=self.settings.sample_rows, ...)

return QueryRun(
    dataframe=df,        # ← UI・保存・必要部分の追加参照用
    summary=summary,     # ← 保存用。agentはDataFrameから小さいCSVまたはスキーマを作る
    ...
)
```

小さい結果は全列・全行をヘッダー付きCSVで渡します。型・欠損・取得範囲は
CSVの外に短いメタデータとして添えます。次は説明用に一部のメタデータを省略した例です。

```json
{
  "executed_sql": "SELECT grade, COUNT(*) AS cnt FROM ... GROUP BY grade LIMIT 1000",
  "bytes_processed": "9.58 MB",
  "result": {
    "delivery": "csv",
    "row_count": 2,
    "column_count": 2,
    "columns": [
      {"name": "grade", "dtype": "str", "null_count": 0},
      {"name": "cnt", "dtype": "Int64", "null_count": 0}
    ],
    "csv": "grade,cnt\n学部1年,320447\n学部2年,154374\n",
    "null_marker": "\\N",
    "sent_row_count": 2,
    "rows_omitted": 0,
    "complete": true,
    "source_truncated": false
  }
}
```

`src/token_budget.py`が初回返却を決めます。既定100行以下かつ推定データ予算内なら
上記のCSV形式、それ以上は`delivery="schema"`として結果ID・列名・型・行数だけを返します。
101〜1,000行は中規模、1,001行以上は大規模として、Geminiが次の分析を選びます。

`analyze_result`は`describe_data`・`aggregate`・`top_k`・`filter_data`・`compare_groups`・
`correlation`・`detect_outliers`・`analyze_timeseries`などを提供します。固定機能に収まらない
計算には、保存済み`data`表に対する読み取り専用SQLite SELECTも使えます。

分析結果は既定最大50行・推定8,000トークン以内でCSVにし、必要なら目標4,000トークンまで縮小します。
CSVには列の型・欠損の表現・取得範囲を添え、値を暗黙に切りません。表示用DataFrameは既定5,000行まで保持します。
`SAMPLE_ROWS`は履歴保存用の旧形式サンプル上限です。現在の初回返却行数は`MAX_DIRECT_ROWS`で決まります。

要約専用の追加Gemini呼び出しはありません。分析結果も保存し、結果IDを指定して再分析できます。
`recall_context`による過去の結果参照と`action="present"`での表示も維持します。
全行のページ取得は最後の手段とし、集計・統計・絞り込み・Top-Kを先に使います。

既定はInteractions APIで、`previous_interaction_id`と新しい質問・ツール結果だけを送ります。
選択中のツール定義・システム指示・思考設定は各回に指定します。
ツール結果は、送信直前にJSON文字列へ変換して`function_result.result`へ格納します。
API側のオブジェクト変換で空配列・空オブジェクトが型なしの空値として拒否されることを避け、
「未確認事項0件」を示す`open_questions: []`やnull・false・0などの値を保持します。保存原本は辞書のままです。
状態ID、原本内の送信済み位置、原本との整合性を確認するハッシュを会話履歴に保存します。
モデルの思考・署名はAPI側で引き継ぎ、画面・原データの保存には引き続きローカルの会話原本を使います。

直前の実入力・出力と次の差分の概算が`GEMINI_STATE_MAX_INPUT_TOKENS`（既定32,000）の80%に達した場合、
またはAPI側の7日保持期限が近づいた場合は、確定条件・要点・結果ID・最新の未確認事項から新状態へ引き継ぎます。
旧形式の会話も同じ方式で再開し、SQL全文や過去のCSVをまとめて再送しません。
進行中の直近ツール結果は未読の値を失わないよう復元入力に含めます。
復元メモは`MAX_HISTORY_TOKENS`以内とし、要点にない数値は`recall_context`・`analyze_result`で再確認します。
期限切れの404は状態IDの取得でも確認し、モデル・エンドポイントの404を期限切れと誤認しません。

確認待ちのツール要求と処理済み応答は保存し、承認後の再開で同じ呼び出しを重ねて実行しません。
通信失敗で状態ID・送信済み位置は進めず、通信失敗・5xxに対する生成の自動再試行を無効にします。
SDK 2.18.1のInteractionsは通常の`attempts`指定だけではPOSTを再試行するため、
生成クライアント側の再試行設定も無効化し、500応答・タイムアウトでHTTP送信が1回になることを検証しています。
明示的に拒否された429のみ、約2・4・8秒にランダムな待機を加え、最大3回再試行します。
`Retry-After`があれば待機時間を尊重し、30秒を超える指定では早期再送せず待機を案内します。
待機中の進捗と停止に対応し、再試行は同じ入力のAPI生成だけに限定してSQL・ツール実行を繰り返しません。
再試行後も429が続く場合は、同じ質問で時間をおいて試す案内を表示します。
ユーザーによる停止・中断した履歴の復元時は、未完了のAPI状態へ無条件に追加せず要点から再開します。

APIが返す実入力・出力・思考・キャッシュ利用量と、送信した差分の推定量は分けて記録します。
差分送信でもモデルが参照する文脈は増えるため、入力トークンや料金が差分だけになる保証はありません。
費用表示と月次制限は既存の標準単価による推定を維持し、キャッシュ割引は別記録です。
`GEMINI_API=generate_content`では従来の履歴要点化・送信予算制御を使用します。

処理例・設定・SQL境界・観測項目は[表データの段階的分析](analysis-layer.md)にまとめています。

### キャッシュ

同一会話内で同じ問い合わせを繰り返させません。状態は `ToolContext` が持ちます。

| キャッシュ | キー | 効果 |
|---|---|---|
| `schema_cache` | `dataset.table` | 同じテーブルのスキーマを再取得しない |
| `listing_cache` | `tables:{dataset}` | 一覧を再取得しない |
| `query_cache` | **SQL 文字列のハッシュ** | 同じ SQL を再実行しない（＝再課金しない） |

SQL のキーは外側の空白だけを除去した元の文字列を SHA-256 でハッシュ化します。
文字列リテラル内の空白・改行・コメントは変更しません。前処理で検索条件を変えて
異なる SQL の結果を再利用することを防ぎます。
サイドバーに現在のキャッシュ件数が表示されます。

## 5. SQL ガード

Gemini が生成した SQL は、**必ず** `check_sql()` を通ってから実行されます。
`SYSTEM_INSTRUCTION` の指示は破られる可能性がある前提で、コード側が機械的に強制します。

### キーワード検査と構文解析

コメント・文字列・バッククォート識別子をマスクしたうえで、先頭が SELECT / WITH で
あること、複文でないこと、危険キーワードが含まれないことを確認します。
さらに SQLGlot の BigQuery 方言で構文解析し、読み取りクエリであることを検証します。
構文を解析できない SQL は実行しません。SQL は書き換えず、元の SQL を BigQuery に渡します
（外側の LIMIT の自動付与を除く）。

### データセット allowlist

構文木のテーブル参照をすべて検査し、`BQ_ALLOWED_DATASETS` 外のデータセットと
別プロジェクトを拒否します。JOIN・カンマ結合・CTE・サブクエリ・UNION の内部も対象です。
列の別名（`l.name`）、文字列、コメントはテーブルとして扱いません。
修飾された UDF も参照先を検査し、参照先を検証できないテーブル関数は拒否します。

1要素の参照は CTE などのために許可します。クエリジョブには default dataset を設定せず、
修飾なしの実テーブル参照は BigQuery 側で拒否される仕組みを維持します。

### LIMIT の自動付与

外側に `LIMIT` が無ければ `DEFAULT_ROW_LIMIT`（既定 1000）を付与し、
付与した事実を画面と Gemini の双方に通知します。集計クエリの場合は
「グループ数が上限を超えると切り捨てが起こる」旨も添えます。黙って切り詰めると
結果を誤読させるため、明示することを優先しています。

## 6. コスト確認の中断と再開

dry run の推定スキャン量が `DRY_RUN_CONFIRM_BYTES`（既定 1GB）を超えると、
ループは**その場で止まって UI に戻ります**。3 ファイルにまたがる流れです。

```
bq_tools.run_query()
    dry run で閾値超過を検出 → ConfirmationRequired を送出
        ↓
agent._run_query()
    _Pending に包み直す
        ↓
agent.run()
    ctx.resume_calls に「処理中だった function_call 群」を退避
    ConfirmationPending を返してループを抜ける
        ↓
app.render_confirmation()
    推定スキャン量と SQL を提示し、承認 / 拒否ボタンを描画
    押されたら ctx.decisions[key] に記録
        ↓
agent.run() を再度呼ぶ
    ctx.resume_calls から同じ地点で再開
```

### 再開が安全な理由

再開時は退避した function call 群を**先頭から再ディスパッチ**します。
これが安全なのは、ツールが冪等だからです。

- `list_datasets` / `list_tables` / `get_table_schema` — 読み取り専用
- `run_query` — SQL のハッシュで `query_cache` を引くため、再実行も再課金も起きない

**この冪等性を壊すと、ユーザーが承認した瞬間に二重課金が発生します。**

承認 / 拒否のキーは、Gemini が送ってきた**元の SQL** のハッシュです
（`sql_guard` が LIMIT を付与した後の SQL ではありません）。再開時に同じ引数で
再ディスパッチされるため、元の SQL を基準にする必要があります。

## 7. 結果の表示

単一の数値や理由の説明は文章を中心に、推移・比較・分布は最後の回答用クエリから
原則1つのグラフを表示します。「表で」「一覧にして」は表、「グラフで」はグラフを
優先し、探索・検証用の途中結果は図表の自動表示対象にしません。
同じ結果の図表は自動で再表示せず、明示的な表示依頼があれば再表示します。

「データ・実行詳細」には、クエリとローカル分析それぞれの短い説明を折りたたみの見出しとして並べます。
分析は方法・対象列・集計/抽出条件・分析元/条件一致/結果/AIへの返却行数・実行時間を表示します。
保存済み結果へのSQL分析ならSQLも表示し、分析結果を表・CSVで確認できます。
分析だけを行った回答、失敗・停止した処理の途中結果も記録し、会話履歴から復元します。
図表はGeminiが種類・軸・内訳を指定し、アプリが利用者の表示指定・型・集計粒度・重複表示を確認して最終決定します。
説明をクリックすると、そのクエリの表・SQL・実行量を展開します。初期状態は閉じています。
表は CSV で取得でき、回答本文に既に表示した表は折りたたみ欄に重複表示しません。
棒グラフは先頭の指標の合計による上位10カテゴリまでとし、該当カテゴリの内訳はすべて保持します。
全件は折りたたみ欄で確認できます。

処理中の表示は一覧・列情報の確認、データ取得・集計に合わせて切り替えます。
ツール実行後は直前の進捗を維持し、`finish_answer`が返った時に「回答を作成しています」と表示します。
取得・集計中は Gemini が作成した `purpose` を表示し、実行詳細にも同じ説明を使います。

処理中は丸の中に四角のある停止ボタンを表示します。ターンはバックグラウンドで実行し、
UI は進捗を表示しながら停止要求を受け付けます。停止すると追加のツール呼び出しを止め、
実行中の BigQuery ジョブにはキャンセルを要求します。送信済みの Gemini リクエストは
終了を待つ場合があります。停止した処理のツール応答を補って会話を復旧し、途中結果と
利用量を保持して次の質問を受け付けます。実行中は履歴の切り替えを無効にします。

単純な件数・合計の質問には数値と単位を添えて簡潔に、傾向・理由・考察の質問には
比較や時系列の変化などの根拠を示して説明するよう指示します。文字数や段落数の
固定指定はありません。

確認質問の前に関連するテーブルのスキーマと必要な値を確認し、分析可能な選択肢を
用意するよう指示しています。スキーマを一つも取得していない場合は、アプリ側も
`ask_clarification` を拒否し、先にスキーマを確認するようモデルに返します。

期間・店舗・指標などが曖昧な場合、`ask_clarification` が質問と2〜5個の選択肢を
生成して処理を中断します。Gemini は排他的な条件には `selection_mode=single`、
複数を同時に指定できる条件には `multi` を指定します。画面はボタン形式で表示し、
選択肢には1〜5の番号が付き、クリックまたは同じ数字キーで選択・解除できます。
単一選択でも再選択で解除でき、自由記述への入力中は数字キーで選択を変更しません。
選択肢は自動選択せず、自由記述のみ、
または選択肢と補足で回答できます。空の回答では再開せず、元の質問を引き継ぎます。
選択形式を含む確認待ち状態も会話履歴に保存し、形式のない旧履歴は単一選択で表示します。

グラフの種類・X軸・Y軸・必要な内訳は、Geminiが`run_query`の`chart`で指定します。
通常の分析ツール呼び出しに含めるため、グラフ専用の追加Gemini問い合わせはありません。
時間・年月の推移は原則折れ線、カテゴリ比較は原則棒グラフとし、時間は横軸に置きます。
内訳が必要な場合だけ`color`にカテゴリ列を指定し、Y軸は1つの数値列にします。
折れ線は色別の系列、または複数の数値列を同じグラフで比較できます。棒グラフは積み上げの内訳になります。
散布図は数値同士の関係、面グラフは量・構成の推移を示す場合に選びます。
円グラフ（`pie`）は少数カテゴリの構成比を示し、`x`をカテゴリ、`y`を非負の数値1列にします。
負数・欠損・合計0・カテゴリの重複・結果の切り捨てがある場合は表へ戻します。
円グラフには棒グラフ用の上位10件への絞り込みを適用しません。
ヒートマップ（`heatmap`）は`x`を横軸、`row`を縦軸、`y`を濃淡に使う数値1列にします。
軸の組ごとに1行であることを検証し、存在しない組を0で埋めません。
円・ヒートマップでは`color`を指定せず、Vega-Liteで描画します。不要なら`kind=none`です。

```json
{"kind": "line", "x": "月", "y": ["来店数"], "color": "店舗"}
```

指定列・数値型・内訳の粒度はサーバーで検証します。存在しない列、Y軸の非数値列、
同一X軸・内訳の組の重複などがある場合は表に戻し、暗黙の集計による誤表示を避けます。
種類・X軸・Y軸の手動選択欄は設けません。変更したい場合は会話で依頼します。
同じSQLでもキャッシュ済み結果に異なるグラフ指定を適用でき、再実行・再課金はしません。
グラフ指定は履歴に保存します。指定のない旧履歴では従来のdtypeによる推定を利用します。

## 8. エラーの二経路

同じ例外を、宛先ごとに変換し分けます。

| 変換 | 宛先 | 内容 |
|---|---|---|
| `friendly_error(exc)` | UI（回答本文） | 平易な日本語 |
| `technical_detail(exc)` | Gemini | 構文エラーの内容などをそのまま渡す |

Gemini には技術的詳細を渡します。エラー内容が分からないと自力で SQL を
修正できないためです。ツール実行中の例外は `agent._dispatch()` が捕捉して
`{"error": ...}` として tool response に載せ、**ループは止めません**
（Gemini に再試行させます）。

失敗した `run_query` の SQL と技術的詳細は、回答本文には出しませんが、
画面の「診断情報」expander（折りたたみ表示）には出します。原因調査のために
あえて UI 側にも残していますが、常に見える回答文には混ぜない、という区別です。

# 日本語データを扱う上の注意

対象データセット `202506` には、テーブル名・列名が日本語のものが多数あります
（14 テーブル中 11 個が日本語を含む: `来店`、`日報`、`日次データ`、`月次データ`、
`月毎目標値`、`イベント`、`ユーザー`、`目標値`、`Meetup参加` ほか）。

- データセット名 `202506` は数字始まりのため、修飾なしでは書けません。常にバッククォート。
- **`AS` のエイリアスにもバッククォートが必要です。** BigQuery は裸の日本語識別子を
  `Illegal input character` で拒否します。

  ```sql
  SELECT COUNT(*) AS 件数    FROM `proj.202506.来店`   -- 構文エラー
  SELECT COUNT(*) AS `件数`  FROM `proj.202506.来店`   -- OK
  ```

  実データ検証で踏んだ落とし穴で、`agent.SYSTEM_INSTRUCTION` に明示的な指示として
  入れてあります。

入力トークンを減らすためのメモ・階層要約・詳細参照は、[設計と制約](context-budget-proposal.md)を参照してください。
